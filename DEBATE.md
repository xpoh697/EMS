## [2026-06-27 01:57] Задача: ELEC heating not selected despite cheaper electricity at 15:00

**Контекст:** При SOC=100%, генерации PV=4.18 кВт·ч и cost_per_c_elec=0.0037 PLN/°C (vs gas 0.0133),
система выбирает GAS (0.1411 PLN) вместо ELEC. Пользователь справедливо указал: нужно сравнивать
стоимость запасённой энергии, а не абсолютные затраты сессии.

**Корень проблемы:** DP сравнивает суммарные PLN:
- GAS: 0.1411 PLN → 8.5°C прирост (5°C выше t_min=40°C)  
- ELEC: ~0.175 PLN → 47°C прирост (29.4°C выше t_min) → 4.7× эффективнее за °C полезной энергии

DP не вознаграждает ELEC за запасённую полезную тепловую энергию выше t_min.

---

### Archi

**Решение:** Добавить `storage_reward` в ELEC mode блок (boiler_dp_engine.py ~строка 722).
Вознаграждать каждый кВт·ч полезной тепловой энергии, запасённой выше t_min, по ставке
маржинальной экономии против газа:

```python
useful_rise = max(0, T_elec_end - t_min) - max(0, T_elec_cooled - t_min)
storage_reward = useful_rise * (c_per_gas - c_per_elec)
```

**Результат для 15:00:**
- useful_rise = 29.4°C
- reward = 29.4 × (0.0133 - 0.0037) = 0.282 PLN
- net ELEC cost = 0.175 - 0.282 = -0.107 PLN → DP выбирает ELEC ✅

---

### Skeptic

**Проблема 1 — Double-counting:** DP уже должен моделировать bypass-выгоду в будущих слотах.
Reward может дублировать эту выгоду.

**Проблема 2 — Отрицательный net cost:** Без cap reward > cost → net < 0 → жадный перегрев
электробойлера при любых условиях, включая ночь с высокой ценой.

**Проблема 3 — Разные объёмы:** 1°C в 50L электробойлере ≠ 1°C в 200L газовом.
Нужно сравнивать в кВт·ч через eff_elec_only, не в °C.

---

### Заключение

**Консенсус достигнут за 2 итерации:**

1. **Double-counting не реален** — bypass-выгода за горизонтом 48ч не учитывается DP (электробойлер
   при 60°C держит bypass 80+ часов), terminal reward тоже слаб. Storage reward заполняет "слепое пятно".

2. **Cap обязателен:** `storage_reward = min(storage_reward, cost * 0.85)` → net_cost всегда > 0.

3. **Нормализация в кВт·ч через eff_elec_only** вместо сравнения в °C.

**Финальный код:**

```python
if tariff <= 0.0:
    reward = temp_reward * (max(0.0, T_gas_end_val - t_min) + max(0.0, T_elec_end_val - t_min)) + 0.01 * kwh
else:
    useful_kwh = max(0.0,
        (T_elec_end_val - t_min) - max(0.0, T_elec_cooled - t_min)
    ) / eff_elec_only if eff_elec_only > 0.0 else 0.0
    if useful_kwh > 0.0 and c_per_gas > tariff:
        gas_kwh_rate = c_per_gas * eff_elec_only
        storage_reward = useful_kwh * max(0.0, gas_kwh_rate - tariff)
        storage_reward = min(storage_reward, cost * 0.85)
    else:
        storage_reward = 0.0
    reward = storage_reward
```


**Применить в:** `boiler_dp_engine.py` строки ~719–722 (ELEC mode reward block).

## [2026-06-30 12:27] Задача: с чего вдруг электро бойлер изолирован

### Archi

Электробойлер изолирован (bypass = OFF, или клапан перекрыт) по штатной логике управления. 
Сейчас система находится в режиме `Auto`, текущее действие — `IDLE` (целевой сетпоинт 40.0 °C, средняя температура системы 41.1 °C, то есть нагрев не требуется).
В `boiler_dp_engine.py` для режима `IDLE` условие подключения электробойлера имеет вид:
`T_bypass_end_val = (T_elec_prev >= t_min)`
Так как текущая температура электробойлера составляет `39.0 °C`, что ниже целевого сетпоинта `40.0 °C` (`t_min`), оптимизатор решает перекрыть клапан (`bypass = False`), чтобы не подмешивать остывшую воду из электробойлера в систему отопления и ГВС.
В UI это отображается как "Изолирован" с оранжевым предупреждающим цветом/иконкой `mdi:alert-circle-outline`.

### Skeptic

В текущем поведении есть три проблемы:
1. **Ложное предупреждение в UI:** Отображение нормального рабочего состояния (изоляция электробойлера при простое) с иконкой предупреждения `mdi:alert-circle-outline` и оранжевым/красным цветом вводит пользователя в заблуждение, заставляя думать, что произошла авария.
2. **Отсутствие гистерезиса в DP-движке:** В отличие от локального фреймворка (где `t_min - 6.0` / `t_min - 7.0`), в `boiler_dp_engine.py` используется жесткое пороговое сравнение `T_elec_prev >= t_min`. При колебаниях температуры около 40°C это может приводить к дерганью клапана между часовыми интервалами.
3. **Рассогласованность с локальным фолбэком:** Локальная логика в `boiler_controller.py` при отсутствии рекомендаций от DP переключает байпас по порогам `t_min - 6.0` и `t_min - 7.0` (то есть при 39°C он остался бы подключенным!), в то время как DP-движок отключает его сразу при падении ниже `t_min` (40°C). Это вызывает рассинхронизацию между планировщиком и исполнением.

1. Дать пользователю детальный ответ на его вопрос: электробойлер изолирован автоматически, потому что его температура (39.0°C) опустилась ниже целевого сетпоинта (40.0°C) в режиме простоя (IDLE), чтобы холодная вода из него не охлаждала систему отопления.

Предложить исправление в UI (`boiler-card.js`): заменить пугающую иконку `mdi:alert-circle-outline` для состояния 'Изолирован' на нейтральную (например, `mdi:circle-off-outline` или `mdi:valve-closed`) и убрать класс `warn` с ноды клапана, если это штатный режим простоя, либо сделать предупреждение только при ручных ошибках/авариях.

## [2026-06-30 12:29] Задача: какого хуя он туда сюда включается выключается?

### Archi

В коде обнаружена циклическая обратная связь (петля/гонка) между планировщиком DP и локальным контроллером:
1. DP планирует нагрев `GAS` с байпасом `OFF` (так как бойлер холодный, `T_elec = 39.0 < 40.0`).
2. Локальный контроллер видит `GAS`, но `T_elec > threshold + 1.0` (`39.0 > 35.0`), поэтому он решает задержать запуск газа (`_gas_heating_delayed = True`) и принудительно открывает байпас (`ON`), чтобы выработать тепло из электробойлера.
3. Байпас меняет значение на `ON`.
4. Изменение байпаса триггерит перерасчет DP-сенсора (через `sensor.dp`).
5. DP-сенсор запускается с `bypass_start = True`. Он видит, что бойлер подключен, но его температура ниже целевой, и решает перейти в режим `IDLE` (выключить газ) и закрыть байпас (`bypass = False`), чтобы не охлаждать систему. Он выдает `IDLE` с `recommended_bypass = OFF`.
6. Контроллер видит режим `IDLE` от DP. Так как режим сменился с `GAS` на `IDLE`, локальный контроллер сбрасывает `_gas_heating_delayed = False` (потому что мы задерживаем только `GAS`).
7. Контроллер закрывает байпас (`OFF`) согласно рекомендации DP.
8. Байпас закрывается (`OFF`), это снова триггерит DP.
9. DP видит закрытый байпас и потребность в тепле и опять рекомендует `GAS`. Цикл замыкается.

Для решения нужно изменить условие сброса `self._gas_heating_delayed` в `boiler_controller.py`. Мы не должны сбрасывать флаг задержки газа при переходе в режим `IDLE`, если эта задержка еще активна по температуре (`T_elec > threshold`). Мы сбросим его только тогда, когда температура упадет ниже `threshold` или DP переключится в активный электрический нагрев (например, `ELEC`).

### Skeptic

В предлагаемом решении есть 3 уязвимости/проблемы:
1. **Отсутствие проверки на None для `t_elec`:** При проверке температуры `t_elec <= threshold` в блоке `IDLE` датчик может вернуть `None` (например, если он временно недоступен). В этом случае сравнение вызовет `TypeError` и упадет вся функция `_async_apply_current_dp_plan()`. Нужно обязательно обернуть проверку в `if t_elec is not None`.
2. **Неявный выход из задержки при изменении уставки:** Если пользователь или система резко изменят целевую температуру (`t_min`), `threshold` изменится. Нужно убедиться, что `t_min` берется актуальный на момент каждой проверки в `IDLE`.
3. **Бесконечный IDLE при зависании датчика:** Если датчик температуры электробойлера зависнет на высоком значении (например, `39°C`) и больше не будет обновляться, контроллер навсегда застрянет в режиме задержки газа с включенным байпасом. Нужен защитный таймаут или проверка доступности данных.

### Заключение

1. Переписать логику сброса флага `self._gas_heating_delayed` в `boiler_controller.py`:
   - Если DP рекомендует `GAS`, мы проверяем температуру и входим в задержку (байпас `ON`), если `t_elec > threshold + 1`.
   - Если DP рекомендует `IDLE`, и задержка уже была активна, мы сохраняем ее активной, пока `t_elec > threshold` (при условии, что `t_elec` не `None`).
   - Если `t_elec <= threshold` или датчик вернул `None`, мы сбрасываем `_gas_heating_delayed = False`.
   - При любых других режимах (например, `ELEC`) задержка безусловно сбрасывается.
2. Использовать безопасный доступ к сенсорам и проверку типов.
3. Добавить подробное логирование переходов состояний для отладки SRE.

## [2026-07-01 13:30] Задача: Устранить проблему влияния текущего оверрайда на расчет оверрайда по SOC для будущих часов

### Archi
Привет! На скриншоте виден баг: на 16:00, 17:00 и 18:00 при SOC=100% отображается режим `Export PV` (`sale_pv_no_bat`), хотя время уже после полудня и заряд больше 90%.
Причина в том, что в цикле обхода `schedule` при проверке условий мы использовали переменную `active_override`, которая считывается только для текущего часа (в данном случае, 13:00):
`is_high_soc_override = (slot_hour >= 12 and slot_soc > 90.0 and active_override is None)`
Поскольку в 13:00 был активен ручной оверрайд (отображается значок руки), `active_override` был равен `"self_consume"` (не `None`). Это привело к тому, что условие `active_override is None` вернуло `False` для всех последующих интервалов плана, полностью отключив логику переключения в `sale_pv`.
Для решения проблемы мы должны проверять оверрайд персонально для каждого конкретного слота:
```python
slot_date = slot.get("date", today_str)
slot_override = overrides.get(slot_date, {}).get(str(slot_hour))
```
И затем использовать `slot_override is None` в условиях вместо `active_override is None`.

### Skeptic
Три замечания к фиксу Archi:
1. **Безопасность приведения типов:**
   При чтении оверрайда для слота мы используем `str(slot_hour)`. Сам `slot_hour` должен быть гарантированно приведен к `int` безопасным образом с обработкой исключений, чтобы не вызвать падение при некорректных форматах. Это у нас уже сделано, так что риски минимальны.

## [2026-07-08 14:15] Задача: Батарейка полностью заряжена, цена экспорта еще 3 часа нулевая, электробойлер не включен и панели просто душаться вместо того что бы нагреть бойлер!!!

### Archi

Проблема вызвана положительной обратной связью (deadlock) в логике отсечки дефицита солнечной генерации (`self._solar_deficit_cutoff`):
1. В безэкспортном режиме `stop_sale` (curtail_pv = True) инвертор принудительно ограничивает (душит) генерацию PV до уровня текущего потребления дома, когда батарея полностью заряжена.
2. Датчики фиксируют, что разница `Avg PV - Avg Load` близка к нулю.
3. Поскольку разница меньше 2500 Вт, локальный контроллер бойлера считает, что избытка солнца нет, и оставляет отсечку дефицита `_solar_deficit_cutoff` активной.
4. Отсечка `_solar_deficit_cutoff = True` блокирует ТЭН электробойлера.
5. Из-за выключенного ТЭНа нагрузка дома не растет, и инвертор продолжает душить генерацию.

Решение:
В режиме ограничения генерации (`curtail_pv = True`) при достаточном уровне заряда батареи (SOC >= лимита режима, например 90% для `stop_sale`) принудительно деактивировать отсечку по дефициту солнца (`self._solar_deficit_cutoff = False`). Это позволит ТЭНу включиться, после чего инвертор автоматически раздушит панели для компенсации нагрузки в 2.5 кВт.

### Skeptic

Три замечания к предложенному обходу отсечки:
1. **Защита от облачности при пограничном SOC:** Если SOC равен 91% (чуть выше порога 90%), а солнце реально пропало (тучи), ТЭН мощностью 2.5 кВт начнет разряжать батарею.
   *Ответ Archi:* Разряд батареи будет кратковременным: как только SOC опустится ниже 90%, условие обхода перестанет выполняться, обычный мониторинг дефицита активирует отсечку и выключит ТЭН. Это безопасно и саморегулируемо.
2. **Дребезг контактов реле (Chattering):** Если SOC колеблется около порогового значения (например, 90.0% и 89.9%), ТЭН будет постоянно включаться и выключаться.
   *Ответ Archi:* Введем небольшой гистерезис по SOC (1.0%): активируем обход при `SOC >= limit_soc`, но снимаем его только если `SOC < limit_soc - 1.0%`.
3. **Безопасность датчиков:** Датчик SOC батареи может вернуть `None`, `unknown` или `unavailable`. Нужно корректно обрабатывать эти состояния и не допускать падения логики.
